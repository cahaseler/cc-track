# Implementation Plan: Migrate to Claude Code Plugin System

**Feature ID**: `101`
**Branch**: `101-migrate-to-claude-code-plugin-system`
**Created**: 2025-10-15
**Spec**: @.claude/specs/101-migrate-to-claude-code-plugin-system/spec.md

## Summary

Migrate cc-track from npm package distribution to native Claude Code plugin system. This migration restructures the codebase to follow plugin conventions (commands/, hooks/, lib/, scripts/, templates/), eliminates compiled binary distribution in favor of direct TypeScript execution via Bun, and creates a dedicated marketplace repository for plugin distribution. The migration preserves all existing functionality while improving discoverability, installation simplicity, and integration with the Claude Code ecosystem.

**Primary Requirement**: Enable users to install and manage cc-track as a Claude Code plugin instead of an npm global package.

**Technical Approach**: Restructure existing TypeScript codebase to match plugin directory conventions, update semantic-release to version both package.json and plugin.json, create marketplace repository, and provide migration guide for existing npm users.

### Key Integration Points

#### Environment Variables
- `${CLAUDE_PLUGIN_ROOT}`: Plugin directory path (provided by Claude Code)
- Used in slash commands to reference plugin files
- Example: `!bun run ${CLAUDE_PLUGIN_ROOT}/commands/complete-task.ts`

#### Configuration Management
- Per-project config stays in `.claude/track.config.json`
- Plugin reads config from project directory, not plugin directory
- Config schema unchanged from current implementation

#### Dependency Detection
- Check for npm package: `which cc-track` or `npm list -g cc-track`
- Check for Bun: `which bun`
- Check for plugin dependencies: verify `node_modules/` in plugin directory

### Quickstart Guide

#### For New Users
1. Add marketplace: `/plugin marketplace add cahaseler/cc-track-marketplace`
2. Install plugin: `/plugin install cc-track@cc-track-marketplace`
3. Navigate to project: `cd /path/to/project`
4. Install plugin dependencies: `cd $(dirname $(which claude-code))/../plugins/cc-track && bun install`
5. Run setup: `/setup-cc-track`
6. Enable desired features through interactive prompts
7. Start using: `/specify "your feature idea"`

#### For Existing npm Users
1. Backup `.claude/` directory (optional but recommended)
2. Uninstall npm: `npm uninstall -g cc-track`
3. Follow "New Users" steps above
4. Verify existing projects work with plugin version

## Risk Assessment

### Technical Risks

- **Risk**: Claude Code plugin system API changes during beta
  - **Likelihood**: Medium (plugin system in public beta)
  - **Impact**: High (could break compatibility)
  - **Mitigation**: Follow official conventions strictly, monitor Claude Code releases, test with each Claude Code update

- **Risk**: Import path breakage during restructuring
  - **Likelihood**: High (moving all files)
  - **Impact**: High (tests would catch but time-consuming)
  - **Mitigation**: Systematic approach, update tests alongside moves, verify at each step

- **Risk**: Semantic-release dual versioning failures
  - **Likelihood**: Low (@semantic-release/git is well-tested)
  - **Impact**: Medium (version sync issues)
  - **Mitigation**: Test thoroughly in CI, manual verification before each release

- **Risk**: User data loss during migration
  - **Likelihood**: Low (migration preserves .claude/ directory)
  - **Impact**: Critical (users lose work)
  - **Mitigation**: Explicit backup instructions, migration guide emphasizes preservation, no automatic file deletion

### Dependency Risks

- **Risk**: Bun installation issues for users
  - **Likelihood**: Medium (some users may not have Bun)
  - **Impact**: Medium (blocks usage)
  - **Mitigation**: Clear error messages, installation documentation, dependency verification in setup

- **Risk**: Plugin dependency installation failures
  - **Likelihood**: Medium (network issues, permission problems)
  - **Impact**: Medium (blocks usage but recoverable)
  - **Mitigation**: Clear error messages with exact commands, troubleshooting guide

- **Risk**: npm/plugin coexistence conflicts
  - **Likelihood**: High (users may forget to uninstall npm)
  - **Impact**: Medium (confusing behavior)
  - **Mitigation**: Explicit detection and blocking with clear instructions, README emphasizes npm removal

### Migration Risks

- **Risk**: Users skip migration guide steps
  - **Likelihood**: Medium (users may rush)
  - **Impact**: Medium (broken installations)
  - **Mitigation**: Step-by-step guide with checkboxes, verification steps, Claude can help guide through process

- **Risk**: Multiple projects at different migration stages
  - **Likelihood**: High (per-project migration)
  - **Impact**: Low (this is expected and supported)
  - **Mitigation**: Clear documentation that npm/plugin can coexist globally, per-project detection prevents conflicts

## Implementation Notes

### Key Patterns to Follow

From system_patterns.md:
- **File-based state management**: All state in `.claude/` directory
- **Hook-based architecture**: Event-driven, stateless hooks
- **Safety first**: Never overwrite files, create backups, check existence
- **Clear error messages**: Guide users to solutions
- **TypeScript source over binaries**: Easier maintenance, no build step

Plugin-specific patterns:
- **Use ${CLAUDE_PLUGIN_ROOT}**: Never hardcode plugin paths
- **Separate hooks per event**: edit-validation.ts, pre-tool-validation.ts (not unified)
- **Templates as references**: Don't copy, reference from plugin directory
- **Per-project config**: .claude/track.config.json stays in project

### Testing Strategy

**Unit Tests**:
- Update all import paths from `src/` to plugin root structure
- Test npm detection logic (mock `which cc-track`)
- Test dependency verification (mock bun/node_modules checks)
- Test configuration loading from .claude/ directory
- All existing 366 tests must pass after migration

**Integration Tests** (optional):
- Plugin installation flow
- Command execution via ${CLAUDE_PLUGIN_ROOT}
- Hook registration and execution
- Template reference resolution

**Manual Testing**:
- Install plugin in fresh Claude Code instance
- Run through quickstart guide
- Test migration from npm version
- Verify all slash commands work
- Verify hooks trigger correctly
- Test dependency error messages

### Performance Considerations

- **Hook execution**: TypeScript via Bun executes in <100ms (faster than compiled binary load)
- **Command execution**: Direct TypeScript execution eliminates build step overhead
- **Plugin load time**: Claude Code loads hooks on-demand, minimal impact
- **Template access**: Reading from plugin directory vs copying has negligible performance difference

### Breaking Changes

- **Installation method**: npm global install → Claude Code plugin
- **Command invocation**: Some internal command paths change (but slash commands hide this)
- **Distribution**: npm registry → GitHub marketplace
- **Build artifacts**: No more dist/ binaries

**Non-breaking**:
- All `.claude/` project files remain compatible
- Slash commands work identically from user perspective
- Configuration schema unchanged
- Hook behavior unchanged (just different registration method)
