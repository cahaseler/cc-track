## Summary

Create a `/context-maintenance` slash command that provides Claude with comprehensive, structured instructions for cleaning up context files (system_patterns.md, decision_log.md, progress_log.md, etc.) to reduce bloat and improve focus. The command uses a static markdown approach with hybrid guidance: explicit rules for common cleanup scenarios combined with general principles for cases requiring judgment.

**Technical Approach**: Single static markdown file containing cleanup instructions, no TypeScript logic needed.

## Phase 0: Research & Decisions

### Research Questions
1. What context files exist in a typical cc-track project?
2. What types of bloat commonly accumulate in each file type?
3. What cleanup patterns are safe vs. risky?

### Key Decisions

#### Decision: Static Markdown Instructions
- **Chosen**: Single markdown file with comprehensive guidance
- **Rationale**:
  - Simplest possible implementation (YAGNI)
  - Easy to maintain and update based on user feedback
  - No runtime dependencies or complexity
  - Claude excels at following detailed written instructions
- **Alternatives Considered**:
  - Dynamic analysis (TypeScript script): Over-engineered, adds complexity and dependencies
  - Hybrid approach: Unnecessary complexity for a guidance-focused feature
- **Tradeoffs**:
  - Static means no file-specific analysis (acceptable - hybrid guidance covers this)
  - Requires comprehensive instructions upfront (one-time cost)

#### Decision: Hybrid Guidance Model
- **Chosen**: Mix explicit rules with judgment-based principles
- **Rationale**:
  - From clarification: User requested hybrid approach
  - Explicit rules handle common cases efficiently
  - Judgment principles handle edge cases and context-specific decisions
  - Balances consistency with flexibility
- **Alternatives Considered**:
  - Pure explicit rules: Too rigid, can't handle all scenarios
  - Pure judgment: Too vague, inconsistent results
- **Tradeoffs**:
  - More upfront work to define good rules and principles
  - But results in better, more reliable cleanup process

#### Decision: File-by-File Guidance Structure
- **Chosen**: Organize instructions by context file type (system_patterns.md, decision_log.md, etc.)
- **Rationale**:
  - Each file type has different purposes and bloat patterns
  - Makes instructions easier to follow sequentially
  - Natural workflow: tackle one file at a time
- **Alternatives Considered**:
  - By cleanup type (duplicates, outdated, etc.): Harder to follow, requires jumping between files
  - Single comprehensive checklist: Too long, easy to miss file-specific nuances
- **Tradeoffs**: More structure upfront, but clearer execution

## Phase 1: Design & Contracts

### Command Structure

The `/context-maintenance` command will have this structure:

#### 1. Introduction
- Purpose and goals
- When to run this command
- Safety reminder (git provides rollback)

#### 2. General Principles (applies to all files)
- **Explicit Rules for Common Cases**:
  - Remove duplicate information across files
  - Consolidate similar patterns into single entries
  - Remove outdated version references (e.g., "TypeScript 4.x" when now on 5.x)
  - Delete obsolete decisions superseded by later ones
  - Trim verbose Update Log sections aggressively
- **Judgment Principles for Edge Cases**:
  - Preserve context that explains "why" over "what"
  - Keep patterns still in active use
  - Maintain decision rationale even if implementation changed
  - Balance completeness with focus

#### 3. File-Specific Guidance

##### system_patterns.md
- **Common Bloat**:
  - Deprecated patterns no longer used
  - Duplicate pattern descriptions
  - Overly detailed Update Log entries
- **Cleanup Rules**:
  - Remove patterns not reflected in current codebase
  - Consolidate similar patterns (e.g., multiple testing patterns → one comprehensive entry)
  - Trim Update Log to major milestones only
- **Preserve**:
  - Active patterns in current use
  - Rationale for unusual choices
  - Warnings about what NOT to do

##### decision_log.md
- **Common Bloat**:
  - Overly detailed "decision process" narratives
  - Decisions superseded by later ones
  - Low-impact decisions that don't affect architecture
- **Cleanup Rules**:
  - Mark superseded decisions as "SUPERSEDED BY [entry]"
  - Remove "Template Entry" examples if present
  - Consolidate related decisions (e.g., multiple git workflow tweaks)
  - Aggressively trim verbose explanations
- **Preserve**:
  - Major architectural decisions
  - Decision rationale (why chosen, alternatives rejected)
  - Warnings about failed approaches

##### progress_log.md
- **Common Bloat**:
  - Every minor task update
  - Verbose session descriptions
  - Duplicate status updates
- **Cleanup Rules**:
  - Keep only major milestones and completed tasks
  - Remove session-by-session play-by-play
  - Consolidate status updates for same task
- **Preserve**:
  - Completed task summaries
  - Major pivot points or direction changes
  - Learnings from completed work

##### Other Context Files
- **product_context.md**: Focus on current state, remove outdated goals
- **code_index.md**: Remove entries for deleted files, update paths
- **user_context.md**: Keep recent learnings, remove outdated preferences
- **backlog.md**: Remove completed items, consolidate similar suggestions

#### 4. Workflow
1. Start with system_patterns.md (usually most bloated)
2. Move to decision_log.md
3. Then progress_log.md
4. Finally other context files
5. Review diffs before saving

#### 5. Completion Checklist
- [ ] All files reviewed
- [ ] Duplicate information consolidated
- [ ] Outdated references removed
- [ ] Update Log sections trimmed
- [ ] Important context preserved
- [ ] Diffs reviewed for accidental deletions

## Risk Assessment

### Technical Risks
- **Risk**: Instructions too vague, Claude makes poor deletion choices
  - **Likelihood**: Low (hybrid guidance mitigates this)
  - **Impact**: Medium (could delete valuable context)
  - **Mitigation**: Clear examples, explicit rules for common cases, reminder to review diffs

- **Risk**: Instructions too prescriptive, can't handle edge cases
  - **Likelihood**: Low (judgment principles cover edge cases)
  - **Impact**: Low (user can always provide additional guidance)
  - **Mitigation**: Hybrid approach balances rules with judgment

### Dependency Risks
- **Risk**: Command format incompatible with Claude Code slash command system
  - **Likelihood**: Very Low (using established markdown format)
  - **Impact**: High (command wouldn't work)
  - **Mitigation**: Use same format as existing commands, test early
