# Implementation Plan: Task Orchestration System Overhaul

**Feature ID**: `110`
**Branch**: `110-task-orchestration-system-overhaul`
**Created**: 2025-12-07
**Spec**: @.cc-track/specs/110-task-orchestration-system-overhaul/spec.md

## Summary

Overhaul the `/cc-track:tasks` command to produce a phase-based TDD breakdown where each phase is executed by specialized subagents (stub writer, test writer, implementer, validator) coordinated by an Opus orchestrator. Parallel phases run as background agents. The orchestrator reviews subagent output, manages checkpoints, and escalates complications.

---

## Alternatives Considered

*Considered during specification session with user.*

| Alternative | Approach | Tradeoff | Why Rejected |
|-------------|----------|----------|--------------|
| Code-based orchestrator | TypeScript script that programmatically dispatches agents | More control | Fights against Claude Code's prompt-first model |
| Hybrid (script + prompt) | Script generates structure, prompts drive behavior | Predictable structure | Adds complexity, harder to iterate |

**Selected**: Prompt-only approach because it aligns with existing cc-track commands, is easier to iterate, and Claude Code's native tooling handles the mechanics.

## Research Summary

Research completed via parallel background agents (see research-*.md files):

### Key Patterns Adopted

**From AIDD (Eric Elliott)**:
- Separation of concerns: Spec → Plan → Tasks → Progress
- "Given X, should Y" requirement format for testability
- Complexity assessment before orchestration
- Explicit approval gates between phases

**From Superpowers (Jesse)**:
- Fresh context per task (subagent isolation)
- Code review gates between work items
- Evidence-based completion (tests must pass, not just "look right")
- Two-track model: fast (subagent-driven) vs controlled (batched with review)

**From Anthropic feature-dev**:
- Parallel exploration/review via background agents
- Confidence-based filtering for reviews (≥80% only)
- Decisive design (commit to one approach, don't present options)

**From Background Subagents Research**:
- `run_in_background: true` enables parallel execution
- `AgentOutputTool` with `block: true` waits for completion
- No polling - post status update, then wait

## Design Decisions

### Decision: Prompt-Only Implementation
- **Chosen**: All orchestration logic in markdown command/agent files
- **Rationale**: Aligns with existing cc-track pattern, easier to iterate, Claude Code handles mechanics
- **Alternatives Considered**: TypeScript orchestrator, hybrid approach
- **Tradeoffs**: Relies on Claude following complex prompts accurately

### Decision: Four Specialized Subagents
- **Chosen**: Stub Writer, Test Writer, Implementer, Validator
- **Rationale**: Clear separation of concerns, tool restrictions enforceable per role
- **Alternatives Considered**: Fewer agents with broader scope
- **Tradeoffs**: More agents = more coordination, but cleaner TDD enforcement

### Decision: Haiku for Subagents, Opus for Orchestrator
- **Chosen**: Haiku (fast/cheap) for scoped work, Opus (capable) for coordination
- **Rationale**: ~5x speed, ~90% cost reduction for file I/O heavy work
- **Alternatives Considered**: Sonnet for complex implementations (orchestrator can still choose this)
- **Tradeoffs**: Haiku may struggle with very complex tasks (orchestrator escalates)

### Decision: Background Agents for Parallel Phases
- **Chosen**: Use `run_in_background: true` for `[P]` marked phases
- **Rationale**: True parallelism, orchestrator context preserved
- **Alternatives Considered**: Sequential execution only
- **Tradeoffs**: Coordination complexity, but significant time savings

### Decision: "Stop and Settle" Escalation Pattern
- **Chosen**: On complication: stop new work, wait for in-flight, update status, THEN raise issue
- **Rationale**: Prevents background agents interrupting human conversation
- **Alternatives Considered**: Immediate escalation (interrupts user)
- **Tradeoffs**: Slight delay before user sees issue, but cleaner UX

## Implementation Approach

### Deliverables

**1. Agent Definitions** (4 files in `agents/`)

| Agent | Purpose | Tool Restrictions | Model |
|-------|---------|-------------------|-------|
| stub-writer | Create minimal file stubs with exports | Write, Edit (*.ts only, no test files) | Haiku |
| test-generation | Write tests, run tests, report output | Write, Edit (*.test.ts only), Bash(test commands) | Haiku |
| implementer | Implement production code, run tests | Write, Edit (*.ts, no test files), Bash(test commands) | Haiku |
| validator | Verify phase requirements met | Read, Grep, Glob (read-only) | Haiku |

**2. Tasks Command Overhaul** (`commands/tasks.md`)

Transform from task-list generator to phase-based TDD orchestration:
- Generate phases (testable functionality chunks)
- Each phase has 4 steps: Stub → Tests → Implement → Validate
- Mark parallelizable phases with `[P]`
- Declare dependencies between phases
- Include status checkpoints for user approval
- Present for approval before implementation

**3. Tasks Template Update** (`templates/tasks-template.md`)

New structure with:
- Phase format (not task list)
- Step definitions within phases
- Checkpoint markers
- Orchestration instructions for execution

### Orchestration Flow (for tasks.md command)

```
1. Read plan.md and spec.md
2. Identify testable functionality chunks → Phases
3. Determine phase dependencies and parallelizability
4. Generate tasks.md with:
   - Phase definitions (Phase 1, Phase 2, etc.)
   - Each phase has: Stub step, Tests step, Implement step, Validate step
   - [P] markers for parallel phases
   - Dependency declarations
   - Checkpoint placements
5. Present to user for approval
6. On approval, begin orchestrated execution:
   a. For each phase (respecting dependencies):
      - Dispatch stub-writer subagent
      - Dispatch test-generation subagent (runs tests, reports failures)
      - Dispatch implementer subagent (runs tests, reports results)
      - Dispatch validator subagent (verifies requirements met)
      - Update tasks.md checkbox
   b. For parallel phases:
      - Dispatch all as background agents
      - Post status update ("Waiting for Phase 2, 3, 4...")
      - AgentOutputTool with block: true
      - Collect results before dependent phases
   c. At checkpoints:
      - Pause, summarize progress
      - Wait for user approval
   d. On complication:
      - Stop delegating new tasks
      - Wait for in-flight agents
      - Update tasks.md status
      - Raise issue with user
```

## Risk Assessment

### Technical Risks
- **Risk**: Haiku struggles with complex implementation tasks
  - **Likelihood**: Medium
  - **Impact**: Low (orchestrator can use Sonnet instead)
  - **Mitigation**: Orchestrator has discretion on model choice; clear escalation path

- **Risk**: Subagents don't follow tool restrictions
  - **Likelihood**: Low (enforced by agent YAML frontmatter)
  - **Impact**: Medium (could modify wrong files)
  - **Mitigation**: Tool restrictions in agent definitions; validator catches issues

- **Risk**: Background agent coordination issues
  - **Likelihood**: Low (confirmed working in research)
  - **Impact**: Medium (phases run sequentially instead)
  - **Mitigation**: Fallback to sequential; clear dependency declarations

### Process Risks
- **Risk**: Prompts are complex, Claude may not follow accurately
  - **Likelihood**: Medium
  - **Impact**: Medium (incorrect execution)
  - **Mitigation**: Test with real feature; iterate on prompt wording
